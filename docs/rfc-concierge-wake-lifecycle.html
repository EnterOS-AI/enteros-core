2. Why the fixes kept failing

Each attempt fixed one symptom in isolation inside a system with no single owner of the flow. A fix in one place was raced or undone by another; two attempts (the greeting-first status gate, #4606) failed review because they patched a delicate state machine without owning it end-to-end.

3. The design flaw

Three uncoordinated mechanisms emit the onboarding self-turn (the "fallback" is a branch of the greeting, not a fourth peer), and many more self-wake types exist beyond onboarding (self-cron, self-scheduler, self-goal-nudge, self-lifecycle…). None share an owner:

"Make core own everything" fixes consistency but does not scale: a core on the hot path of every turn/log/wake, holding a live socket per agent, is a throughput wall and a single point of failure. The discriminator is decision-frequency + consistency need:

Reconcile model + the contract that must be pinned NOW

Mechanism = level-triggered reconciliation (Kubernetes-style) over the existing heartbeat, not a live command socket. But the review found that greet-once is a one-shot effect, not a pure level — greeting twice is a visible bug — so the reconcile shape alone is insufficient. These contract items are "the shape," not deferrable scale machinery; retrofitting them later is a protocol break + data migration:

  • Wake idempotency key threaded decision → dispatch → delivery → marker. The only thing that makes exactly-once greeting survive retries, reconnects, and a future sharded gateway. #1 priority.
  • Marker-commit timing — decision-time vs confirmed-delivery. Covers the two windows the link-down rule ignores: decided-but-undelivered (greeting lost forever) and delivered-but-unreported (double greet). This is the same race class we're eliminating, relocated to the decide/deliver boundary.
  • Desired-state generation on a versioned heartbeat envelope (k8s observedGeneration) so stale vs new desired state is distinguishable.
  • Session-id namespacing — decide canvas-<wsid> vs canvas-<org>-<wsid> now; it is written into the message store (migration to change later).
  • Log pointer granularity — per-session, not per-turn, or per-turn frequency leaks back into the control plane.
Named tension: the heartbeat interval is the greeting-latency floor — "greet now" only arrives on the next poll. The property that makes the mechanism scale (periodic, not live) directly slows the flagship greeting. Pick an interval (with jitter) consciously; a fast-lane nudge for the first greeting may be warranted.

5.5 The one-line agent model + idle behavior contract NEW

The agent is one line. Everything — user turns, the greeting, restart-context, and the idle wake — runs on a single execution line per workspace (the canvas context), sharing one conversation memory. A user prompt is always highest priority and preempts whatever the agent is doing. The idle wake is not a parallel side-thread; it is low-priority work the agent does on that same line when the line is otherwise quiet.

This settles the idle-context question directly. The independent context_id for the idle wake was a workaround to stop a returning user turn from colliding with in-flight idle work — but collision is the wrong thing to avoid. The correct behavior is preemption: the user turn cuts in and wins. So the fix is to put idle back on the one line and arbitrate priority, not to keep it on a detached line.

Idle behavior contract — the flow the idle wake drives:

  1. Fire only after a genuine idle interval — no user turn and no agent tool-calls for the window.
  2. Wake on the current session (one line, full conversation memory), not a fresh context.
  3. The agent triages what's top-priority, and may fan out subagents to work items in parallel (faster, better compute use).
  4. Ack before working: e.g. "No active work from you right now — I'm picking up: <items>. I'll report back as each is done."
  5. Report per work item as it completes (visible in canvas chat — wake prompts are shown, per the resolved decision).
  6. Continue until there's nothing left — no backlog, no long-term goals — then close the idle loop until the next wake.
  7. At any point, a user prompt preempts the idle work and takes over.
Delivery implication. This is more than "forward the final reply." The idle turn emits multiple user-facing messages over its lifetime (the upfront ack + a status per work item) — the agent proactively messages the user via its send-to-user tool, rather than the poster forwarding one response body (idle_digest/poster.py forwards a single reply today). The mechanism must support proactive, multi-message idle reporting on the canvas line, and it must be cleanly interruptible when the user returns.
